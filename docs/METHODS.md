# 方法框架：让 Agent 按需加载可选的记录方法

状态：定稿（2026-10-28）。

## 一句话

研究方式、审计记录、威胁建模这类“方法”以后会越来越多。它们统一放在 Skill 包的 `skills/blackboard/methods/` 里，每个方法是一份带 frontmatter 的 Markdown，格式沿用 [Agent Skills 规范](https://agentskills.io/specification)。Agent 先看一行一个的目录，自己选中了才读正文。内核不读取这个目录，也不为任何方法改变投影、预算或 `lint`。

## 要解决什么

[研究记录方式](INQUIRY.md)确立了一个原则：方法只能是可选参考，不进内核。方法一多，还要回答三件事：

- 怎么让 Agent 知道有哪些方法，又不让一长串方法持续暗示它“应该用一个”。
- 压缩或交接之后，怎么知道已有记录按哪种方法写的。
- 怎么保证新写的方法不悄悄变成任务流程。

## 调研结论

- **渐进披露是通行做法。** Agent Skills 的[客户端实现指南](https://agentskills.io/client-implementation/adding-skills-support)把加载分三层：会话开始只给名字和描述（每个约 50–100 token），选中后读正文，正文提到的资源再按需读。绝大多数实现让模型自己决定读哪个，宿主不做关键词匹配；模型能读文件时，直接读文件就是最简单的触发方式。
- **描述决定会不会被选中。** [描述调优指南](https://agentskills.io/skill-creation/optimizing-descriptions)用“该触发 / 不该触发”两组真实提问测触发率，每条多跑几次，并分开调优集和验证集。
- **规模大了改成检索。** 工具或方法数以百计时，常见做法是先检索再加载（例如延迟加载工具定义、对工具描述做检索），而不是把全部描述放进上下文。
- **项目级来源要过信任。** 指南建议项目目录里的 skill 先经过信任检查才加载；同名冲突的惯例是项目级覆盖用户级。
- **“总是注入”是干预。** 一些编辑器规则支持“总是注入”或“按文件自动挂载”。对 blackboard 来说，这正是 [AGENT.md](../AGENT.md) 所说的投影干预，不借鉴。

## 架构

### 两级目录，不进宿主目录

方法不注册成独立 skill。注册了，每个会话的宿主目录都会列出全部方法，即使任务和 blackboard 无关；这既花上下文，也是一种持续暗示。所以在 blackboard Skill 内部再嵌一层：

| 层 | 内容 | 什么时候读 |
| --- | --- | --- |
| 宿主目录 | 只有 `blackboard` 一个 skill | 会话开始，由宿主决定 |
| `SKILL.md` | 一行入口，指向方法目录 | Agent 已经决定用 blackboard |
| `methods/INDEX.md` | 每个方法一行：名称、版本、何时读、说明、关系 | Agent 想看有哪些方法 |
| `methods/<名称>.md` | 方法正文，及它链接的资源 | Agent 自己选中这个方法 |

`recording.md`、`setup.md`、`parallel-agents.md` 讲的是所有记录都适用的规则，留在 `references/`，不算方法。

### 方法包格式

```yaml
---
name: inquiry
description: 做什么、什么时候可选使用；说明不规定步骤。
metadata:
  version: "1"
  invocation: agent
  relations: answers, refines, supports, contradicts, supersedes
---
```

- `name`、`description` 按 Agent Skills 规范：名字只用小写字母、数字和连字符，与文件名一致；描述 1–1024 字符。
- blackboard 自己的字段都放进规范允许的 `metadata`（值都是字符串）：
  - `version`：方法版本，整数。
  - `invocation`：`agent` 表示 Agent 判断有用时可以自己读；`user` 表示只在用户明确点名时读，例如威胁建模。
  - `relations`：方法用到的关系名。读到不认识的关系名时，可以在目录里反查它出自哪个方法。
- 不加规范以外的顶层字段。格式兼容意味着以后哪个方法要单独发布成 skill，几乎不用改。

### 目录由脚本生成

`methods/INDEX.md` 由 `node scripts/method-index.mjs` 从各方法的 frontmatter 生成，不手改。`--check` 模式和测试保证目录与元数据一致。目录开头说明方法可选、内核不认识、只读选中的那一个。

### 只由 Agent 或用户触发

- 不做关键词匹配，不自动注入；`context`、`lint`、Hook 不提示“可以用某某方法”。
- 用户点名某个方法，等同于用户显式触发。
- `invocation: user` 的方法可以从 `SKILL.md` 的意图表直接链接；其他方法只经由目录到达。

### 交接：方法选择记在黑板上

Agent 选用某个方法后，可以给目标或相关节点加标签 `method:<名称>@<版本>`，例如 `method:inquiry@1`。这是 Agent 写的普通标签，内核照常保存，不解释。压缩后的自己或接手者在 `context` 里看到标签，就知道该重读哪份说明。宿主需要专门保护 skill 内容不被压缩；blackboard 本身就是能熬过压缩的记忆，不必另做。

### 版本

- 同一版本内，关系名和标签只增不改，旧记录始终读得懂。
- 改变某个关系名或记录约定的含义时升版本。标签钉住了版本，所以旧版正文要保留，例如另存为 `<名称>-v1.md`，或在正文里写明各版差异。

### 宪章检查

方法文本本身就是干预渠道：宿主把 skill 内容当作持久的行为指导。所以“方法只讲怎么记录、怎么思考，不规定步骤”不靠自觉，由 `test/methods.test.js` 在 CI 里检查：

- frontmatter 符合上面的格式，方法名不重复，目录已同步。
- `metadata.relations` 与正文里出现的 `--rel` 一致。
- 正文声明自己可选，并说明不规定步骤、顺序或流程。
- 不出现规定步骤的措辞，例如“下一步应当”“必经”“完成标准”“必须先”。
- `SKILL.md` 只直接链接目录和 `invocation: user` 的方法。
- `bin/`、`lib/` 不读取 `methods/`，不认识任何方法标签。

这些检查约束的是方法作者，不是 Agent；内核 `lint` 仍然只提示、退出码为 0。

## 三个决定

1. **方法能讲到什么程度：讲怎么记录、怎么思考，不规定步骤。** 不写先后顺序、完成标准或“下一步应当”。业界的 skill 默认就是完整流程，blackboard 的定位不同，所以用上面的检查守住。
2. **目录先用文件。** 方法在几十个以内时，读 `INDEX.md` 就够，不需要新命令。出现以下任一情况再加只读的 `blackboard methods [search <词>]`：要合并用户级或项目级来源；方法多到需要检索；遇到不能读文件的宿主，届时也可以暴露成 MCP prompts 或资源。内核在这几个阶段都不变。
3. **来源与信任：v1 只有内置方法。** 内置方法随 Skill 包发布，经过 PR 和上面的检查。以后支持用户级或项目级来源时：项目级方法按宿主对该目录的信任决定是否列出，并标明来源；**同名一律不覆盖**，两个都列出、标明来源。这里故意偏离“项目级覆盖用户级”的惯例：方法决定 Agent 记录什么，一个刚 clone 的仓库不应能悄悄替换掉审过的方法。

## 怎么加一个新方法

1. 在 `skills/blackboard/methods/` 新建 `<名称>.md`，写好 frontmatter 和正文。正文开头说明它可选、不用也是正常记录、不规定步骤。
2. 运行 `node scripts/method-index.mjs` 重新生成目录。
3. 运行 `npm test`；`test/methods.test.js` 会检查格式、关系名和措辞。
4. 需要新的关系名时照常使用：内核按未知关系保存。查看器目前只接受内置关系，这是与方法无关的已知缺口，见 [研究记录方式](INQUIRY.md)。

## 验证

- **会不会被选中**：按描述调优指南的做法，给每个方法准备“该用 / 不该用”的任务，各跑几次，看 Agent 读没读这个方法。
- **会不会干扰**：沿用 exp2 的有方法 / 无方法对照，比较任务结果、Agent 的决策顺序是否被改变、多出来的记录成本。方法让记录更好读、但改变了 Agent 做任务的方式，就算干扰。

## 暂不做

- `blackboard methods` 命令、用户级与项目级来源、MCP 接入：等上面的触发条件出现。
- 方法评测的自动化：先在 exp2 里手工跑。
- 让查看器接受未知关系：与方法框架无关，单独处理。
