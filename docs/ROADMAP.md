# blackboard 发展方向

> 日期：2026-10-23 · 基线：`main` 8ccc06d（0.6.0，含 DSH 插件首版）
> 本文是方向建议，不是承诺清单；每一阶段以“完成标准”收口，再决定下一步。

## 一句话

**先验证价值，再扩功能：用小规模真实任务对照试验回答“记下来到底有没有用”；CLI 契约照常小步推进，保证建在内核上的适配层不被悄悄弄坏。**

## 现状判断

blackboard 已经从“Claude 的附加工具”变成多个宿主共用的外置记忆：

| 宿主 | 接入方式 |
| --- | --- |
| Claude Code | Skill + 可选恢复 Hook |
| Codex | 共享 `.agents/skills` |
| DeepSeek Harness（DSH） | `plugins/dsh-blackboard`，通过 CLI 的 JSON 输出桥接 |

最近几轮落地了发布隔离（`release install|use`）、创建时声明关系（`--to`）和查看器可读性。核心的事件溯源、三层分离和不干预原则已经稳定。

项目存在的首要理由（上下文可恢复）还缺少真实使用的证据。本仓库自己的黑板是 57 个 `auto:true` 的 `fact` 节点，其中 15 个带 `loc`，没有一条关系。它们是旧自动采集留下的样本，不能代表当前显式记录方式的效果；没有关系、没有交接，可能来自采集机制、任务类型或入口摩擦，“Agent 看不到记录的回报”只是其中一种假设。

已有、正在进行的工作（尚未合并到 `main`）：

- `scripts/evaluate-recovery.mjs`：7 个确定性场景（中断、反驳、取代、多 Agent 交接、低预算等），检查 `context` 投影是否覆盖必需的节点、事实和证据。它证明**投影正确**，不证明**新 Agent 接得住工作**，两种证据要分开看。
- `lib/history.js`：节点历史投影，保留字段前后值、关系增删和记录者。

## 方向与优先级

### 1. 恢复对照试验：先做

用两三个真实任务做小规模探索性试验，回答“记录是否有助于接续工作”，并用结果决定后续投入。不建评分平台；脚手架可以很快，真实语料和可靠标注才是主要工作量。

**两种恢复情形分开测：**

- **首次接手**：日志截到时点 T，新 Agent 只读 T 时点的完整 `context`。
- **中断续接**：保留中断点 S 时的上下文，再读 S→T 的增量（`context --since S`）。

**三组对照**，固定模型、问题和上下文 token 预算：

1. 普通交接摘要
2. 仅节点
3. 同一批节点 + 关系

关系本身占 token，所以按预算对齐，而不只按节点对齐。

**标准答案只限截至 T 已记录的内容。** 某个理由在 T 之后才首次记录，恢复者回答“未记录”才是正确表现，否则试验会奖励猜测未来。

**除答对率外，还要测：**

- 证据引用是否正确：引用的节点在 T 时存在，且支持该说法。尽量机械检查，少用模型当裁判。
- 是否把猜测说成事实：对照节点的 `confidence`。
- 信息不足时是否恰当地回答“未知”（参考 [LongMemEval](https://arxiv.org/abs/2410.10813) 对拒答能力的单独评估）。
- 恢复耗时、补读次数，以及记录一方的写入成本。

**方法纪律：**

- 任务照常完成，事后再从日志出题；出题者只看截至 T 的日志。执行任务的 Agent 不应知道之后要考恢复。
- 开始前写下什么结果会改变方向。例如，如果交接摘要组不明显落后，说明图结构对恢复贡献有限，重心应转向“记录更便宜”或“人更读得懂”。

完成标准：至少两个真实任务的黑板脱敏后保存为试验语料，三组对照的结果和写入成本有记录；下一项新增能力的取舍引用这些结果。结论限于探索性发现，不宣称通用“恢复分”。

### 2. CLI 契约：并行小步推进

三个宿主在读 CLI 的 JSON，但只有 `context` 声明了格式版本（`blackboard.context.v1`）。已核对的缺口：

- `node add`、`edit`、`link`、`cursor`、`checkpoint`、`status` 的 `--json` 输出没有版本标识，字段一变，适配层会静默出错。
- 写命令在 `.blackboard/` 不存在时会自动初始化。DSH 调研文档已注明桥接层只能在每次写入前自行检查。
- DSH 插件的写入授权直接写死了内核的锁文件和缓存临时文件名，并注明对应 0.6 运行时。

交付：

- 所有 `--json` 输出带 `schema` 版本标识。
- `--version --json` 返回 CLI 版本、`eventVersion` 和接口版本。
- 写命令提供“缺少黑板时报错而不初始化”的选项。
- 内核声明自己会写入的文件，适配层不再依赖内部文件名。
- 在内核仓库加契约测试，固定这些输出格式。

完成标准：DSH 插件只依赖上述公开契约；改动输出字段会让内核测试先失败。

它解决集成可靠性，恢复试验解决产品值不值得用，两者互不阻塞。

### 3. 来源变化提示：第一个候选新增能力

节点已有位置字段 `loc`，缺的是版本校验。代码变了，黑板上的发现仍显得确凿。

- 叫“来源变化提示”，不叫“结论过期判断”：整文件变化、行号移动都不等于证据失效。
- 首版围绕记录区域的内容哈希，只区分三种状态：**内容变化、文件缺失、未检查**。
- `lint` 与 `context` 只读报告，不改可信度、不阻断、不建议下一步；可信度仍由 Agent 决定。
- 新增可选字段，不提升 `EVENT_VERSION`。“移动”与“改变”的区分（附近重新定位片段）留到以后。

完成标准：带 `loc` 的节点在代码改动后能被如实标为三种状态之一；不带哈希的旧节点一律显示“未检查”，不报错。是否在试验之前开工，看第 1 项的初步观察。

### 4. 宿主适配：先做深，再做多

- DSH 第二阶段：自动刷新恢复上下文，并在上下文压缩前后保存检查点。DSH 不保证等待这次写入完成后才压缩，保存时机必须如实说明。
- MCP 的取舍规则：当前不需要 MCP Server（与 DSH 调研结论一致）。如果出现第四个宿主，做一个通用的 MCP 适配，而不是第四个专用适配。

完成标准：DSH 上恢复、分叉会话、压缩和插件热重载都经过验证，失败时不改变 Agent 的下一步决策。

### 5. 查看器：在已有历史上打磨可读性

节点历史的基础已经在 `lib/history.js` 中实现，后续重点是可读性，而不是重做历史系统。

- **检查点归属**：每次变化标明发生在哪个检查点之后，便于对照“中断续接”。
- **提出—反驳—取代**：把一个主张的历史按这条线组织，而不是平铺字段变更。
- **推理路径**：选中一个结论，沿实际记录的关系多跳展开证据链，不推断任何路径。
- **回放时间线**：拖动时间轴查看任一时刻的黑板。
- **为嵌入做准备**：把数据层（`use-graph-stream`）和画布组件分开，这是将来嵌入 DSH 面板的前提。

完成标准：历史与回放只读取事件日志，不写事件、不移动游标；画布组件可以在不依赖 SSE 的情况下单独挂载。打磨的优先顺序随真实使用调整。

## 不做什么

以下做法会侵蚀项目的身份，即使看起来“更智能”也不做：

- 让 LLM 推断或建议关系、建议下一步（违反不干预原则）。
- 把 blackboard 变成 Agent 行动的前置条件，或把节点类型变成状态机。
- 让宿主的会话记录或云端同步成为事实源，制造第二事实源。
- 为每个宿主维护一份内核或 Skill 副本。
- 为恢复试验另建一套评分平台，或用合成黑板的分数代替真实任务的证据。

## 观察项

- **多 Agent 分歧面（暂缓）**：支持和反证并存是正常研究，不同 Agent 先后改置信度也可能是接力改判。真正的分歧需要明确的主张、作者、适用条件和同时存在的不同立场。现在缺真实样本，做检测器容易误报；先在试验和日常使用中收集真实案例，有了样本再评估。
- **回放成本**：每条命令都完整回放日志，成本随日志增长。目前规模下没有问题；日志接近 1 万条事件时再考虑快照或增量回放。
- **敏感内容**：黑板可能含敏感原文。宿主越多，导出和分享时的脱敏越需要跟上；试验语料必须先脱敏再保存。
