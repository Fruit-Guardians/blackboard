# blackboard 发展方向

> 日期：2026-10-27 · 基线：`main` 32abc58（0.6.0）
> 本文是方向建议，不是承诺清单；每一阶段以“完成标准”收口，再决定下一步。
> 上一版（2026-10-23，基线 8ccc06d）的 5 个方向已并入下面的阶段，进展见“已完成”。

## 一句话

**内核已稳，下一步是让它成为可以依赖的基础设施：契约有版本、适配只依赖契约、价值有两块以上真实黑板的证据。三件事做到，标为 1.0。**

## 现状判断

| 层 | 状态 | 依据 |
| --- | --- | --- |
| 内核 | 稳定 | 事件日志是唯一事实源，CLI 是唯一写入路径；每次写入记录作者；Linux、macOS、Windows × Node 18/22/24 的 CI 全部通过 |
| 契约 | 未定 | 8 个 `--json` 输出声明了 schema（如 `blackboard.context.v1`），其余接受 `--json` 的命令没有；没有固定输出的测试，输出变了只有读的人会发现 |
| 适配 | 落后于契约 | DSH 插件仍用环境变量传项目根和身份，读运行时的 `package.json` 并只接受 0.6.x，写入授权写死了 `lock`、`state.json.tmp` 两个内部文件名 |
| 证据 | 一块黑板 | exp1：黑板记录答对 13/14，检查点摘要 4–5/14；但只有一个任务、每组一次、非盲评 |

### 已完成（2026-10-23 以来）

- 写入署名：节点、关系、修改、删除和重置都记录作者；所有写命令接受 `--agent`，所有命令接受 `--cwd`；`--no-init` 让写入在缺少黑板时报错而不新建。`capabilities` 以 `writeAttribution`、`cwdFlag`、`noInit` 声明。
- Skill 改用 `--cwd`/`--agent`/`--no-init`，已知目标时用 `--to` 挂到目标，等待外部时用 `block`，标题只写主张，审计目标写明代码版本。
- Windows CI：`.gitattributes` 固定 LF，打包校验在所有平台通过。
- 恢复试验工具进入 `main`（此前误合进 `docs/charter` 分支），修正了检查器的两处误计：检查点 ID 是有效引用；已推翻或已确认的假设不算猜测。
- exp1（首次接手、中断续接各三组）完成，结果见下一节。

### exp1 告诉了我们什么

| | A 检查点摘要 | B 仅节点 | C 节点 + 关系 |
| --- | --- | --- | --- |
| 首次接手 答对 | 5/14 | 13/14 | 13/14 |
| 中断续接 答对 | 4/14 | 13/14 | 13/14 |
| 材料大小（接手 / 续接） | 0.4 / 0.8 KB | 17 / 31 KB | 20 / 36 KB |

- **记录比摘要强**，而且两种情形一致。摘要把“核心假设仍为 open / suspected”说成了“已验证”，记录保住了这个状态。局限：A 只是一段检查点总结，没有测同样预算下写好的摘要。
- **关系没带来收益**：B 与 C 打平，错在同一题。但这块黑板只有 16 个节点、14 条边，全部塞得进预算，题目多是单节点查找，关系又大多写在了正文里。结论是“这次测不出关系的作用”，不是“关系没用”。
- **增量很贵**：续接材料里“S 以来的变化”有 12.8 KB，比 T 时点的整份上下文还大，答对数没有变化。
- **没决定的事被读成了决定**：B、C 的 4 份答案都把“改名识别留作候选”答成“不会做”。这个未决项写在一个已推翻假设的正文里，没有单独成节点。

## 1.0 的标准

满足以下三条即标为 1.0，之后契约按语义化版本演进：

1. **契约**：每个 `--json` 输出带 schema；固定输出的测试覆盖它们；DSH 插件只依赖公开契约。
2. **适配**：DSH 插件显式传 `--cwd`/`--agent`/`--no-init`，用 `capabilities` 做特性检测，不读内部文件。
3. **证据**：恢复试验在第二块真实黑板上复现，其中至少一块超出 `context` 预算。

阶段 1 和 3 互不阻塞，可以并行；阶段 2 依赖阶段 1。阶段 4 之后的工作不阻塞 1.0；阶段 4 的“未决项单独成节点”只改 Skill，可以随时做。阶段 9、10 都依赖阶段 1：阶段 9 的时间点读取代价小、用处直接，阶段 1 完成后可以最先做；阶段 10 的 ID 规则在阶段 1 里定，实现放在 1.0 之后。

## 阶段 1：契约成文、加版本、有测试

**交付：**

- `docs/CONTRACT.md`：列出公开契约，即命令与参数、`--json` 输出及其 schema、退出码、事件格式、`capabilities` 字段，以及兼容规则。兼容规则沿用 [工程约定](../AGENT.md)：加字段兼容；改语义、删字段或改类型才升 schema 版本。
- 所有接受 `--json` 的命令输出都带 `schema`。写命令的回显（`node add`、`edit`、`link`、`cursor`、`checkpoint` 等）和 `status`、`ls`、`show`、`lint` 是重点。
- `capabilities` 作为版本入口：它已返回 CLI 版本、`eventVersion` 和 `schemaVersion`，再补上每个输出的 schema 列表。不另加 `--version --json`，避免两个入口。
- 固定输出测试：用几份固定事件日志（包括 exp1 的事件前缀）生成每个 `--json` 输出并存档。输出一变测试就失败。加字段时由改动者更新存档并在 PR 里说明；删字段或改语义必须升 schema 版本。这也让试验材料可以按版本复现。
- 内核声明自己会写入的文件：`capabilities` 返回写入目标，如锁文件、缓存和临时文件。适配层的写入授权改读这个列表。
- 决定写命令缺少黑板时的默认行为：保持自动初始化，还是改为报错。随第一个契约版本一起定，并写进 `CONTRACT.md`。
- 决定节点 ID 在黑板合并时的规则：保持短 ID（如 `g3`），合并时重编号并记下映射；或者给 ID 加黑板前缀。ID 出现在每个输出、检查点和交接回执里，1.0 之后再改代价很大，所以随第一个契约版本定。阶段 10 按这条规则实现。

**完成标准：** 任何 `--json` 字段的增删改都会让内核测试先失败；`CONTRACT.md` 里的每一项都有对应测试。

## 阶段 2：适配只依赖契约

**交付：**

- DSH 插件改为显式传 `--cwd`/`--agent`/`--no-init`，不再设置 `BLACKBOARD_CWD`、`BLACKBOARD_AGENT`。
- 用 `capabilities` 做特性检测，去掉对运行时 `package.json` 路径和 0.6.x 的硬编码。
- 写入授权改读 `capabilities` 声明的写入目标，去掉写死的 `lock`、`state.json.tmp`。
- DSH 第二阶段（沿用上一版）：自动刷新恢复上下文，在上下文压缩前后保存检查点。DSH 不保证等待写入完成后才压缩，保存时机必须如实说明。
- MCP 的取舍规则不变：现在不做 MCP Server；出现第四个宿主时做一个通用 MCP 适配，而不是第四个专用适配。

**完成标准：** 删掉内核的任一内部文件名或改动其目录结构，DSH 插件的测试仍然通过；在 DSH 上，恢复、分叉会话、压缩和插件热重载都经过验证，失败时不改变 Agent 的下一步。

## 阶段 3：第二块黑板上的恢复证据（exp2）

方法沿用 [恢复对照试验方案](RECOVERY_EXPERIMENT.md)，针对 exp1 的局限补上：

- **规模**：至少一块超出 `context` 预算的真实黑板。这时要靠关系决定放进哪些节点，图最可能起作用。
- **题目**：加入需要沿关系推几步的问题，例如“若 r1 有误，哪些结论跟着失效”“某个假设现在被哪些结果支持、被哪些反驳”。
- **对照**：加一组“关系不写进正文”的黑板，以及同预算下由 Agent 根据黑板写的摘要（A′），区分“结构”和“信息量”的作用。
- **判分**：`run-check.mjs` 打乱组别标签，对照表另存，盲评。
- **材料**：用固定版本的 CLI 生成，manifest 记录 CLI 版本和 schema，保证可复现。

**事先写下的判定：**

- C 在超预算或多跳题上仍不优于 B：恢复材料默认不带关系图，关系只留给 `lint` 判断归属。
- 续接时“当前上下文 + 变化的节点 ID 清单”不比完整增量差：续接改为前者。
- A′ 与 B 相当：记录的价值主要在信息量，重心转向“记录更便宜”。

**完成标准：** 两块以上真实黑板（脱敏后）作为语料保存；关系是否进入恢复材料、续接用什么格式，这两项决定引用 exp1 和 exp2 的结果。

## 阶段 4：把缺口显示出来

都是 exp1 直接暴露的问题，只陈述记录里的事实，不推断、不建议：

- **状态未跟上证据**：`context` 对 open / suspected 的节点注明“自某检查点起有 N 个 supports / contradicts，状态未变”。只陈述关系和时间，是否改状态由 Agent 决定。
- **未决项单独成节点**：Skill 要求“候选、待定、以后再说”记成 open 的 `question`，不写进其他节点的正文；`context` 把 open 的 question 列成“未决”一段。不新增节点类型。
- **未连关系可见**：创建节点时没有关系的，回显注明“未连关系”。
- **省略可见**：`context` 因数量上限省略内容时，注明省略了多少条、可用 `--limit` 调整。

**完成标准：** 在 exp1 的黑板上，hy1 显示为“有支持、状态未变”；改名识别这类未决项记成 open 的 question 后，`context` 的“未决”段列出它。上述输出都有固定输出测试。

## 阶段 5：交接回执

把恢复试验变成日常可用的检查：接手的 Agent 读完黑板后，写一个引用节点 ID 的检查点，复述它理解的现状。`lint` 只做检查器做过的机械核对：

- 引用的 ID 是否存在；
- 引用的节点是否已推翻或作废；
- 是否把 open / suspected 的节点当作已定结论引用。

复用 `recovery-experiment.mjs` 的核对逻辑，不调用模型、不打分、不阻断。

**完成标准：** 用 exp1 的答案作为回执样本，`lint` 报出的问题与检查器结果一致。

## 阶段 6：来源变化提示

上一版的第一个候选新增能力。原型和验证已在本地研究分支 `research/source-change-hints` 完成（场景矩阵、历史回放、性能、兼容实测），尚未推送；下一步是写设计文档 `docs/SOURCE_CHANGE_HINTS.md`，与原型一起提交。

- 基线放节点的兄弟字段 `locBaseline`，不放进 `loc`，不提升 `EVENT_VERSION`。
- 状态：unchanged、intact、moved、changed、missing、unchecked。只读报告，不改可信度、不阻断、不建议下一步。
- `context` 只检查已选入的节点，`lint` 设上限，Hook 和 `digest` 不检查。

依赖阶段 1：新增的 `--json` 字段要进契约和固定输出测试。

**完成标准：** 沿用上一版：带 `loc` 的节点在代码改动后能如实标出状态；不带基线的旧节点一律显示 unchecked，不报错。

## 阶段 7：可靠性、规模与发布

- **性能预算**：[性能文档](performance.md) 已测到 10 万条事件，完整回放 p50 约 54–63 ms，暂不需要快照或增量回放。待办是复测并剖析写入延迟：迭代中的副本单次写入 p50 从约 97 ms 升到约 147 ms，原因未查。然后为 1.0 写下回放、恢复上下文和写入的延迟预算，CI 用 `--quick` 守住它。
- **发布流程**：
  - PR 一律以 `main` 为目标；叠加的 PR 在底层合并后先改目标分支。PR #5 合进已合并的分支、工具几天没进 `main` 就是这样发生的。
  - `main` 的 CI 失败要能被看到。Windows 任务在 `main` 上失败了多个提交才被发现。
- **敏感内容**：试验语料先脱敏再保存（沿用上一版观察项）；导出时的脱敏由阶段 9 的 `--redact` 承担。

**完成标准：** 写入延迟的变化有剖析结论；延迟预算写进性能文档并由 CI 检查；发布清单写进 `docs/ci.md`。

## 阶段 8：查看器

沿用上一版的方向，优先级在上述阶段之后，顺序随真实使用调整：

- 检查点归属：每次变化标明发生在哪个检查点之后。
- 提出—反驳—取代：按这条线组织一个主张的历史。
- 推理路径：沿实际记录的关系多跳展开证据链，不推断路径。
- 回放时间线：查看任一时刻的黑板，复用阶段 9 的时间点投影。
- 数据层与画布分开，为嵌入 DSH 面板做准备。

**完成标准：** 历史与回放只读事件日志，不写事件、不移动游标；画布组件不依赖 SSE 也能单独挂载。

## 阶段 9：时间点读取与导出格式

依赖阶段 1：每个新参数、每种导出格式都是契约的一部分，要有 schema 和固定输出测试。两者都是事件日志的只读投影，不写事件，不产生第二事实源。

**时间点读取（先做）：**

- `context`、`ls`、`show`、`export` 接受 `--as-of <检查点>`：只回放到该检查点为止的事件，得到当时的黑板。
- 参数不叫 `--at`：`--at` 已经是写命令的代码位置参数（`node add --at <路径:行>`），同名不同义会让契约含糊。
- 用途：交接时查看接手之前的现场；审计报告对应到某个检查点；恢复试验直接从真实黑板切出时点，不再手工截取事件前缀。

**导出格式：** `export` 增加 `--format`，默认仍是现在的 `html`。用一个参数而不是多个命令，概念更少。

| 格式 | 用途 | 规矩 |
| --- | --- | --- |
| `markdown` | 审计报告、PR 描述、交接说明 | 按目标分组列出节点、证据和关系；状态、可信度、严重程度照记录原样写出，不总结、不改写 |
| `mermaid` | GitHub 和文档里直接渲染的图 | 只画记录过的关系，`related-to` 用虚线和有向关系区分；超出渲染上限时注明省略了多少 |
| `sarif` | GitHub code scanning、IDE | 只导出带 `loc` 的 `vuln`、`finding` 节点；`level` 只由记录的 `severity` 映射，没记的不从节点类型推断；节点 ID 作为指纹，同一条告警在多次导出之间保持不变 |
| `json` | 其他工具读取 | 节点和关系的完整快照，带 `schema` |

- 所有格式共用 `--as-of` 和 `--redact`。`--redact` 按显式给出的路径和关键词规则脱敏，导出结果注明脱敏了几处。
- 先做 `markdown`、`mermaid`、`sarif`；`json` 等到有工具要读时再做。
- `severity` 到 SARIF `level` 的映射写进 `CONTRACT.md`。
- 阶段 6 完成后，SARIF 结果在 `properties` 里带上来源变化状态（如 changed、missing）。只陈述代码变了，不改 `level`、不隐藏结果、不判断发现是否仍然成立。

**完成标准：** `--as-of` 的输出与把事件日志截到同一检查点后再读取的结果完全相同；每种格式都有固定输出测试；SARIF 输出通过 2.1.0 schema 校验，并能上传到 GitHub code scanning；导出前后事件日志逐字节不变。

## 阶段 10：多块黑板：合并与搜索

依赖阶段 1 定下的节点 ID 规则。不阻塞 1.0。

**跨 worktree 合并：**

- 场景：`.blackboard/` 不进版本库，每个 worktree 各有一块黑板；分支合流时，记录也要合流。
- `merge <另一块黑板的项目根>`：在本黑板的写锁内追加对方有、本方没有的事件，按事件 ID 去重；重复执行不产生变化。只读对方，不改对方的日志。
- 两边都新建了同一个 ID（如 `g3`）时，按阶段 1 的规则处理。合并后，两边原有的引用（检查点、交接回执、正文里的 ID）仍然能解析到原来的节点。
- 两边都改了同一节点的同一字段时，不另造合并规则：两次修改都留在历史里，投影照事件顺序；合并回显和 `lint` 列出这些字段，由 Agent 或人决定。
- 作者署名原样保留；合并回显列出来源、导入的事件数和重新编号的 ID。

**跨黑板搜索：**

- `search <词> --board <项目根>`，可重复：只读，只搜索调用时显式列出的黑板。不维护全局索引，不扫描磁盘寻找黑板，不复制内容。
- 结果带来源黑板；ID 只在各自的黑板里有效，不混在一起。
- 宿主沙箱拒绝读取某个路径时如实报告，其他黑板照常返回。

**完成标准：** 同一对黑板合并两次与合并一次结果相同；合并后，两边原有的每个引用都能解析；跨黑板搜索的结果等于分别在每块黑板上搜索的并集，并且不写任何一块黑板的事件。

## 不做什么

以下做法会侵蚀项目的身份，即使看起来“更智能”也不做：

- 让 LLM 推断或建议关系、建议下一步（违反不干预原则）。阶段 4、5 只陈述记录里的事实。
- 把 blackboard 变成 Agent 行动的前置条件，或把节点类型变成状态机。
- 为了让图“更丰富”增加关系种类或自动连边。关系是否值得进恢复材料由阶段 3 的证据决定。
- 让宿主的会话记录或云端同步成为事实源，制造第二事实源。
- 为每个宿主维护一份内核或 Skill 副本。
- 导出时总结或改写记录，或从节点类型推断严重程度；跨黑板时建全局索引或复制别处黑板的内容。
- 为恢复试验另建评分平台，或用合成黑板的分数代替真实任务的证据。

## 观察项

- **多 Agent 分歧面（暂缓）**：现在有了写入署名，可以看出谁改了什么；但真正的分歧需要明确的主张、适用条件和同时存在的不同立场。先在试验和日常使用中收集真实案例，有了样本再评估。
