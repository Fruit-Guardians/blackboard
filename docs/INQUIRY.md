# 研究记录方式：作为可选的 Skill 参考

状态：定稿（2026-10-27）。本文取代此前同名文件里的内核设计，那一版已撤回。

## 一句话

按“问题 → 候选 → 证据 → 裁定 → 排除与覆盖”来记录研究，是一种可选的记录方式，放在 Skill 的参考 [`references/inquiry.md`](../skills/blackboard/references/inquiry.md) 里。内核不认识它，也不为它改变任何投影、预算或 `lint`。Agent 用不用、用哪种方式，都由它自己决定。

## 背景

exp1 暴露的几处失误都和研究的骨架有关：

| exp1 现象 | 缺的是什么 |
| --- | --- |
| “改名识别留作候选”写在已推翻假设的正文里，B、C 的 4 份答案都读成“不会做” | 搁置的方向没有自己的节点 |
| open / suspected 的假设有支持证据，摘要说成“已验证” | 读者把“有支持”当成“已裁定” |
| `related-to` 占 14 条边里的 5 条，关系没带来收益 | 边没有说清候选在回答什么 |
| “检查过、没问题”的结论无处安放 | 否定结果和覆盖范围没有写法 |

## 为什么不进内核

此前的版本让 `context` 按这个骨架投影现场：加一个 `inquiries` 段，把候选按状态分组，排在邻域之前占预算，并注明“自检查点起有几条新证据、状态未变”。这些都不写数据、不推断，但会通过 Agent 看到什么来引导它：

- **措辞会催促**：“有支持、状态未变”每个字都是事实，读起来却像“该确认了”，可能让 Agent 为消掉提示而过早裁定。
- **预算会转移注意力**：骨架排在邻域之前，预算紧时会挤掉 Agent 正在看的节点周围的内容。
- **结构会被套用**：投影按这种方式组织，Agent 会在不需要的任务里也去凑候选、补边。
- **`lint` 会诱导回填**：提示“问题关闭了但没有答案”，会让 Agent 为消提示去补记录，而“查不出”“不值得查”本来是合法的结束。

[AGENT.md](../AGENT.md) 因此写明：投影也是干预的途径，内核只按记录本身如实呈现，不按某种研究方式组织现场；研究方式只作为可选参考提供，不强制。

## 做了什么

- 新增 [`skills/blackboard/references/inquiry.md`](../skills/blackboard/references/inquiry.md)。开头说明它是可选的，不用也是正常记录；内容只讲怎么记，不讲先做什么：
  - 五个要素对应的节点、状态和关系；
  - 约定关系名 `answers`（候选 answers 问题），内核按未知关系照常保存；
  - 裁定只由 Agent 写，证据多少不等于已裁定；
  - 没决定的方向单独成节点（`deferred` 的候选，或 open 的 `question`）；
  - 否定结果在标题里写明范围，`detail` 写未覆盖部分；
  - 怎么读回来：`search --rel answers --related-to <问题>`、`show <候选> --json`；
  - 审计、调试、探索三种研究的记录侧重。
- `SKILL.md` 的“按需读取参考”加一行入口；`audit.md` 加一句指向它。
- 内核、契约、查看器都不改。

## 现有 CLI 已经够用

用这种方式记录不需要新命令，已核对：

- `node add … --to <问题ID> --rel answers` 和 `link … --rel answers --label …` 都能写入。
- `search --rel answers --related-to <问题ID> --json` 列出回答某个问题的候选及其状态。
- `show <候选ID> --json` 的 `parents` 带每条证据边的种类。
- `context` 照常按类型和状态分段，`answers` 边连同 `label` 出现在关系列表里。

不足之处：`node add --to` 不接受 `--label`，要多执行一次 `link`；页面编辑只能选内置关系，`answers` 只能用 CLI 写。

## 与研究方式无关的内核缺口

核对时还看到几处读取一侧的问题。它们不属于任何研究方式，是否修、怎么修，按“是否如实呈现”单独评估，不在本文范围：

- `context` 里节点不带自己的关系，证据只出现在扁平、受预算裁剪的关系列表里。
- `deferred` 的节点在 `context` 里落进“其他节点”一段，没有按状态单独呈现。
- `show` 的文本输出只列下游、不列上游，而且下游每一行的关系名显示为 `undefined`（读的是节点的 `kind` 字段，实际字段是 `edge`）。
- `node add` 不接受 `--label`。
- 查看器的服务端拒绝不在内置列表里的关系，与“未知关系必须可保存”不一致。

## 撤回的内容

此前版本里的以下设计全部撤回：`context` 的 `inquiries` 段及其预算位置、`evidenceSinceCheckpoint` 和“状态未变”的标注、`unexplained-refutation` 与 `closed-question-without-answer` 两条 `lint`、把 `answers` 加进内核的 `EDGE_KINDS`、`digest` 和 `show` 的按问题分组显示。

## 验证

exp2（路线图阶段 3）检验只靠这份可选参考能不能修掉 exp1 的失误：

- **对照**：同一任务，一组 Agent 可以读到这份参考，一组读不到；投影完全相同。
- **恢复质量**：沿用 exp1 的判分方式，重点看搁置项是否被读成否定、未定的候选是否被说成已验证。
- **是否干扰**：比较两组 Agent 下一步的选择、写入量，以及在证据不足时改裁定的次数。可以读到参考的一组如果明显更早下结论或写得更多，说明这份参考本身在引导，需要再收。

## 与路线图的关系

- **阶段 4（把缺口显示出来）**：“未决项单独成节点”是记录约定，由这份参考覆盖。其中“`context` 把 open 的 question 列成未决一段”是内核投影，要按如实呈现的原则重新评估。“状态未跟上证据”的标注有催促裁定的风险，需要重新审视后再决定做不做。
- **阶段 3（exp2）**：按上面的验证方法加对照组和干扰指标。
- **阶段 5（交接回执）**：不受影响。
